## Cycle-7 design (most consequential)

### 1. Polymarket dynamic taker fee in PnL

Per Polymarket's published schedule (https://docs.polymarket.com), per-leg fee in USDC is:

```
fee = shares * fee_rate * p * (1 - p)
```

where `p` = share price (=YES-mid for YES positions; =(1-mid) for NO positions) and `shares = size_usdc / position_price`. Both legs are taker fees. Maker fees are 0; settlement is 0.

Category → fee_rate table (hardcoded in `cfg.trade.polymarket_fee_rates`):

| category | rate | peak fee /100sh at p=0.5 |
|---|---|---|
| crypto | 0.072 | $1.80 |
| economics / culture / weather / general | 0.05 | $1.25 |
| finance / politics / tech / mentions | 0.04 | $1.00 |
| sports | 0.03 | $0.75 |
| geopolitics | 0.00 | $0 (free) |

Resolver is case-insensitive substring match — Gamma's `"Politics"` and `"us-politics"` both resolve to 0.04.

`trade_closures` schema gains two audit columns: `entry_fee_usdc`, `exit_fee_usdc`. Both are already folded into `realized_pnl_usdc`; the columns exist so you can sum total fees per cycle via:

```sql
SELECT SUM(entry_fee_usdc + exit_fee_usdc) FROM trade_closures WHERE cycle_id=?
```

The closure write is refactored into a free function `write_trade_closure(db, *, trade, exit_mid, close_reason, trade_cfg, category=None, now_iso=None)` so callers other than the closer (notably the markets-stage auto-close) can use it directly.

### 2. Markets-stage auto-close (CLOB tokens going dark)

Cycle 5's Trade #37 (Delhi Capitals IPL) exposed this: when Gamma drops a market from `active=true`, the CLOB orderbook is purged and `clob.get_mid` returns None. The closer's `skip_on_missing_mid=True` policy then holds the trade forever (timeout 24h is the only escape).

Fix: after `_deactivate_missing` flags markets as `active=0`, find any non-closed `trades` on those markets and call `write_trade_closure` with `close_reason='market_resolved'` and `exit_mid = entry_mid`. Gross PnL = 0, net PnL = -(round-trip fee). Conservative — we don't yet query Gamma for the actual resolution (YES vs NO won); doing so would unlock proper $1/$0 settlement. **TODO: layer that on later.**

### 3. Market-weight vs news-weight gate

Cycle-5 audit caught three "smelly" trades opened on far-future / extreme-priced markets where ordinary news shouldn't have moved them:

- `NATO withdraw by 2027 @ mid=0.928` (EVOLVING) — market 7 months out, 92.8% YES already priced
- `Rajasthan Royals IPL 2026 @ mid=0.875` (EVOLVING) — 87.5% YES already priced
- `Tom Steyer wins CA Gov @ mid=0.767` (BREAKING) — 76.7% YES on a thin market

New gate `market_news_imbalance` in `app/stages/trade.py` between `mid_degenerate` (cycle 4) and `min_edge`. Five sub-rules:

1. `thin_market` — `volume_usdc < $10k` (defensive: skipped when volume is 0/NULL because the markets parser doesn't reliably populate the field; tracked as separate bug)
2. `extreme_mid_no_breaking` — mid ∈ [0.15, 0.85] excluded AND freshness != BREAKING
3. `far_future_no_breaking` — days_to_expiry > 180 AND freshness != BREAKING
4. `near_expiry` — days_to_expiry < 1 (regardless of freshness)
5. `singleton_on_extreme_mid` — cluster_size = 1 AND mid in extreme zone

The "BREAKING bypasses extreme-mid/far-future" expresses the user's principle: super-fresh super-important news CAN move a big market; ordinary news can't.

Verified against cycle-29 trades:
- #33 NATO 0.928 EVOLVING → rejected ✓
- #36 Rajasthan 0.875 EVOLVING → rejected ✓
- #34 Epstein 0.115 BREAKING → passes (BREAKING bypass)
- #35 Steyer 0.767 BREAKING → passes (not extreme + BREAKING)
- #37 Delhi 0.500 EVOLVING → passes (not extreme)

## Open follow-ups for next session

1. **markets.py volume parser** — every market in our DB has `volume_usdc = 0` or NULL despite Gamma returning real numbers (e.g. Rihanna market: $750k). The parser at `app/stages/markets.py:_parse_gamma_row:184` looks correct (`float(raw.get("volume") or 0.0)`); something in the upsert or the actual Gamma response shape on subsequent calls must be losing the field. Worth one focused debug session. Once fixed, the `thin_market` sub-rule of the new gate becomes active.

2. **Markets-stage auto-close: Gamma outcome lookup** — currently settles at entry_mid (PnL=−fees). To get proper $1/$0 settlement, query `gamma-api.polymarket.com/markets?condition_ids=<id>&closed=true` for `outcomePrices` after deactivation, and translate to exit_mid via the YES/NO direction. ~20 lines.

3. **Markets-stage `category` field** — Gamma doesn't return a top-level `category` key; the field stays NULL for every market we've polled. We need to derive category from `feeType` (e.g. `general_fees` → general, `politics_fees` → politics) or from the `tags` array. Until then, every trade falls back to default_fee_rate=0.05.

4. **Cycle 5.1's R-rate is still 70-80%** — Phase F (prompt fix) was queued for "only if R% climbs". It stayed flat for cycle 6a but tier-2 expansion lifted call volume, so R-count is now higher in absolute terms. Consider scheduling Phase F if cycle 8 shows the same pattern.

5. **DKG path market_news_imbalance gate** — Fix #7 in cycle 5.1 added the mid_degenerate gate to dkg_trade.py. The same imbalance gate hasn't been ported. DKG fires rarely so low priority, but worth doing for parity.

6. **Throughput overlay + speed overlay plots** — useful diagnostic, but the speed bars currently show "ingest → match" timings in the 50+ second range due to scheduler scheduling, not actual processing. We should add per-function internal timings (the CLT-friendly IID measurements) to complement the end-to-end julianday diffs.

7. **CLT-based required-n** — cycle-29 dashboard showed `match → trade (gate cascade)` needs n=145 for ±10% of mean. We already had n=990 — converged. The other stages (ingest→match, ingest→trade) have heavy tails from poll-wait variance — those aren't strictly IID. Worth instrumenting process-time only.
