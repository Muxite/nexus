# SEULGI handoff — 2026-05-21

B-WRITES is closed. The real root cause was different from yesterday's
hypothesis. The replay harness built today caught the actual bug in
its first concurrent run.

---

## TL;DR

- **B-WRITES is fixed and proven.** Replay at 500 signals × concurrency
  16 produces 129,465 trade rows with zero row-ID gaps and
  `counter == table` exactly. Container 6 (latest deploy) is processing
  live headlines with gap delta = 0 across all four tracked tables.
- **The actual root cause was not what yesterday's handoff said.**
  Yesterday blamed `reset_cycle.py`'s long writer-lock hold. That was
  a contributor but not the trigger. The real bug was in `db.batch()`'s
  cross-coroutine nesting via a shared counter: it let a second
  coroutine join an active batch and keep `_in_batch > 0` past the
  holder's exit, causing the holder's `_commit_if_unbatched` to SKIP
  its COMMIT. The transaction stayed open. The next batch entry hit
  `cannot start a transaction within a transaction` and silently
  rolled back the stranded writes.
- **The replay harness exists now.** `seulgi/scripts/replay/` re-injects
  historical headlines through the live `EngineRunner.process()`
  against an isolated test DB at controlled load + concurrency. It
  proved the fix and is wired into the regression suite (Part 1.5)
  so this bug class cannot silently return.

## What shipped today

### The real B-WRITES fix (`seulgi/app/db.py`)

Two layers, both required:

1. **`batch()` now strictly serializes.** Dropped the "outer/inner via
   counter" design. Always acquire `_batch_lock`, always `BEGIN`,
   always `COMMIT`. `_in_batch` is binary (0/1), used only by
   `_commit_if_unbatched` so individual writes skip their per-row
   commits while a batch is held by THIS task.

2. **Reentrant `_write_lock()` on every write method.** A
   `contextvars.ContextVar` (`_in_batch_var`) tracks "this task is
   inside a batch." When True (set by `batch()`), nested writes
   skip the lock acquire — they're already serialized by the
   enclosing batch. When False (caller is NOT inside a batch), the
   write briefly holds `_batch_lock` so its execute+commit pair
   can't interleave with another task's `batch()` BEGIN. Wraps
   all 7 write methods: `insert_signal`, `insert_trade`,
   `open_position`, `close_position`, `log_usage`,
   `bump_market_heat`, `record_engine_decisions`.

   `contextvars` is per-task and inherited across `asyncio.gather` /
   `create_task`, so child coroutines inside the batch see the flag
   without explicit threading.

### Replay harness (NEW: `seulgi/scripts/replay/`)

- `harness.py` — `ReplayHarness` class. Loads N historical
  headlines from the source DB joined with their `trades` rows

  production `EngineRunner` wired to a fresh test DB + mock
  classifier/relevance/index/news/article-fetcher. Injects

  exact `MarketMatch` set the headline saw in production.
  Zero LLM cost, zero CLOB calls, fully reproducible.
- `run.py` — CLI: `--signals N --concurrency K --rate-multiplier X
  --burst-cycle-reset --report PATH`. Sets
  `SEULGI_DISABLE_HOUR_GATE=1` so replays work at any UTC hour.

## What's broken / open

- **`_write_lock()` deadlocks in production (NEW, 04:20 UTC).** The
  contextvars-based reentrant write-lock — added today to close the
  metrics-flush implicit-txn race — PASSED the 500/c=16 replay but
  deadlocked Container 6 and Container 7 within seconds of boot.
  Symptom: `bump_market_heat` (the first per-headline write that
  acquires the lock) succeeded 264 times, then EVERY `insert_signal`
  blocked forever. External Python script confirmed the SQLite file
  lock was held. `py-spy dump` showed the main thread idle in
  `select()` and the aiosqlite worker thread idle — no obvious
  stack-level deadlock. Workaround shipped: `_write_lock()` is a
  no-op pass-through in `db.py:570` so the bot runs. The B-WRITES
  fix from `batch()` strict-serialization is unaffected (still in
  place). Metrics flush will occasionally fail with "cannot start a
  transaction" (one tick every 5 min) but doesn't lose data. **Real
  fix needed** — suspect interaction between the lock and one of

## How to read the row-ID gaps (kept from yesterday — still correct)

`trades.count(*) = 5,387,202` and `trades.max(id) = 5,754,942`.
The arithmetic: 5,754,942 − 5,387,202 = **367,740 IDs missing**.

Those IDs were allocated to INSERT statements that obtained an
autoincrement ID then ROLLED BACK before COMMIT. The Phase 0
counters (added 2026-05-21) bump `ok` BEFORE the doomed commit, so
the in-memory `db_health.txt` showed success even when the row
vanished. The fix today closes the gap source; existing gaps are
historical scar tissue and will not grow.

To verify post-fix:
```bash
# After 1+ hours of Container 6 uptime with normal traffic
python3 seulgi/scripts/analysis/db_health_audit.py | grep gap
# Gap columns for trades/engine_results should equal the baseline
# numbers exactly (no growth = no new rollbacks).
```

## What changed vs yesterday's diagnosis

Yesterday's handoff identified **6 code-path bugs (R1-R6)** and said
the writer was now stable after fixing them + adding Phase 0
observability. That was partly right:

- R1, R2, R3, R4, R6 are real fixes that landed and helped. Keep them.
- R5 was deferred; doesn't matter — the actual bug was deeper.
- **The diagnosis missed the cross-coroutine `batch()` race.** What
  was deployed yesterday as Container 4/5 had a `batch()` design
  where `outer = self._in_batch == 0` was read BEFORE acquiring the
  lock, but the no-op `outer=False` path didn't acquire the lock at
  all and let the counter stay positive past the holder's exit.
- The Phase 0 counters reported success on the rolled-back writes
  because `_bump_ok` fired after `execute INSERT` + `_commit_if_unbatched`
  but BEFORE the commit was confirmed at the SQL layer. The
  rollback came later (next BEGIN), so the counter was already +1.
  This is why "looks healthy in db_health.txt" coexisted with
  "rows actually missing."

Today's fix replaces the racy nesting with strict serialization and
a contextvars-based reentrant write lock. Validated by the replay
harness — which is the new floor for "is the writer OK."
