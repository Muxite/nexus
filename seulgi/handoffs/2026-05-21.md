## The OpenRouter discovery (THE actual story of today)

**Symptom:** Bot stopped producing trades at 2026-05-21T03:05:06.
Every container deploy after that (Container 4-14, ~10 deploys
across the day) showed:
- signals + market_heat + usage_events writing fine
- trades + engine_results: ZERO

**False trails chased:**

1. *Was the writer broken?* No — direct insert_trade test inside
   container worked. Forensic gap delta stayed 0. Replay harness
   showed writes were healthy.
2. *Was the batch() deadlocking?* Partly. Phase B's batch wrap
   had a real cross-coroutine race (counter-based nesting); fixed
   via strict asyncio.Lock. But trades still 0 after the fix.
3. *Was the `_write_lock` reentrant-contextvars bug?* Yes —
   caused a different deadlock. Disabled, trades still 0.
4. *Was the per-engine relevance code broken?* No — direct test
   with realistic args produces 5 trades cleanly.
5. *Was the gather hanging?* Inconclusive — py-spy showed worker
   thread holding result cursor never consumed. Added timeout.
   trader.eval still never logged.

**Actual root cause (found by directly calling `classify_batch` in
isolation):**

```
[ai] OpenRouter 403: {"error":{"message":"Key limit exceeded
(monthly limit). Manage it using https://openrouter.ai/workspaces/
default/keys/801eacf2b428f12d03192dd7a2045c64d0a578ca0eafb99d5187de16bbefea72"}
```

- Relevance LLM 403 → fail-open → all matches scored "YES" with
  `tokens=0` (clue we missed)
- Prediction LLM 403 → all 3 ensemble samples fail → per-market
  fallback (25 individual calls) → all 403 → returns
  `ClassifyResult(NEUTRAL, 0.0, "api_error")`
- Per-market fallback path makes 25 × ~30s timeout = ~12 min
  per headline. With semaphore=6, 200 headlines queued = ~33 min
  to drain.
- Container 14 had **3843 OpenRouter 403 errors** confirmed in
  logs at 12 min uptime.

**Why this looked like a writer bug:** because every other write
worked (signals, market heat, usage, snaps), the missing one
(trades) felt like a write-path issue. Investigation kept going
deeper into writer code when the actual blocker was upstream
LLM failure.

**Lesson logged for `docs/errors_and_fixes.md`:**

> When ONE specific table stops getting writes but adjacent tables
> on the same connection keep writing, the bug is usually NOT in
> the writer — it's that the call path producing those writes
> isn't being executed. Check upstream HTTP / LLM / external
> dependencies BEFORE chasing locks or transactions.

## Diagnostic playbook (when something goes wrong)

```bash
# Is the writer actually losing inserts?
python3 -c "
import sqlite3
con = sqlite3.connect('seulgi/data/seulgi.db')
b = {'signals':2138,'trades':367740,'engine_results':203150,'usage_events':944}
for t in b:
    cnt = con.execute(f'SELECT COUNT(*) FROM {t}').fetchone()[0]
    mx = con.execute(f'SELECT MAX(id) FROM {t}').fetchone()[0]
    print(f'{t}: gap_delta = {mx-cnt-b[t]:+d}')"
# All zeros = writer healthy. Any positive number = new silent rollbacks.

# Is the gather/trader path running?
docker logs jennie-seulgi 2>&1 | grep -cE "matched .* markets|engine .*executed"
# Both > 0 = pipeline running. matched > 0 + executed = 0 = LLM/relevance issue.

# Is the LLM returning errors?
docker logs jennie-seulgi 2>&1 | grep -cE "OpenRouter 4[0-9][0-9]|api_error"
# > 0 = API issue. Check OpenRouter dashboard for billing/limits.

# Quick replay sanity check (30s, no API spend)
docker compose --profile test run --rm seulgi-replay
# Exit 0 = writer is mechanically correct.

# Full regression suite (5 min, no API spend)
N_SIGNALS_STRESS=500 docker compose --profile test run --rm seulgi-replay
```
