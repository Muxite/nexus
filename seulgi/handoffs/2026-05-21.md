# SEULGI handoff — 2026-05-21 (B-WRITES root cause + observability)

Replaces `HANDOFF_2026-05-20.md` for B-WRITES context. The earlier doc
remains useful for the system overview and the broader strategic
"Path B" decision; this one focuses on the writer-stability work that
landed in cycles 5→6.

---

## TL;DR

- The 2026-05-20 scout-mode plan shipped Phases 1-3 but verification
  showed `trades` + `engine_results` still silently froze after each
  cycle reset.
- 2026-05-21 work identified **six concrete code-path bugs** (R1-R6
  in this doc) and added a **Phase-0 observability foundation** so the
  next regression can't hide.
- Forensic evidence: `trades` has **367,740 missing row IDs** (max_id
  5,754,942 vs count 5,387,202), `engine_results` has **203,150
  missing IDs**. Each gap is an INSERT that obtained an autoincrement
  ID then ROLLED BACK silently.
- Likely root cause: **`reset_cycle.py` ran one huge UPDATE loop on a
  second aiosqlite connection** holding the writer lock for the
  duration; the main container's `busy_timeout=30s` elapsed, aiosqlite
  silently aborted in-flight `insert_trade` calls. Confirmed by the
  pattern: signals + usage_events kept flowing (small fast writes
  fitting under the timeout), trades + engine_results froze (writes
  that needed the writer thread during the contention window).

## What shipped this session

### Phase 0 — observability foundation

Every DB write path now emits structured logs + counters. Silent
rollback is no longer possible undetected.

- `seulgi/app/db.py`: each of `insert_signal`, `insert_trade`,
  `record_engine_decisions`, `log_usage`, `open_position`,
  `close_position` is wrapped in try/except that bumps an ok/err
  counter, logs the failure with full traceback, updates a
  `_last_insert_at[<table>]` timestamp, and re-raises so the caller
  sees the cause.
- New `db.write_health() -> dict` returns per-table last-insert
  timestamps, per-method ok/err counters, WAL frame count, busy_timeout.
- New `_write_db_health()` dashboard tile writes
  `seulgi/data/dashboard/db_health.txt` every 30 s.

### Phase 1 — silent-rollback fixes (R1, R2, R3, R4, R6)

- **R1** (`db.py::batch`) — every rollback path now logs the
  triggering exception with traceback and bumps `db.batch.rollback`.
  The original exception is always re-raised (batch is currently
  unused, but the fix prevents the future regression that previously
  bit cycle-4).
- **R2** (`trader.py::_evaluate_market`) — `open_position` runs under
  its own try/except. If it fails after `insert_trade` committed, the
  trade audit row is preserved and the in-memory bookkeeping (cash,
  staked) is rolled back to match.
- **R3** (`engine.py::_run_engine`) — `trader.evaluate` and
  `record_engine_decisions` each have explicit try/except so one
  engine's crash can't contaminate the other 14 engines' commits.
  Failed-engine decisions list is set to `[]`.
- **R4** (`reset_cycle.py`) — UPDATE loop now commits every 50 rows
  with per-chunk wall-clock logging. The main writer never waits
  more than one chunk for the lock (previously: tens of seconds, past
  the 30 s busy_timeout).
- **R6** (`db.py::record_engine_decisions`) — if executemany fails on
  any row, the call falls back to per-row INSERTs so good rows still
  land; failed rows get one log line each + a counter.
- R5 (`_commit_if_unbatched` race) skipped — `batch()` has no callers
  today; would be relevant only if batched commits are re-enabled.

### Phase 2 — cache RO connection

- `Dashboard._refresh_heavy_cache` now runs on a separate aiosqlite
  RO connection (`SeulgiDB.open_ro_clone`) so the 5+ heavy SELECTs
  never serialise with the writer thread. Wait_for timeout bumped
  from 15 s → 30 s. Consecutive failures (≥3) escalate from WARNING
  to ERROR.

### Phase 3 — metrics flush re-enabled

- `metrics.start_flush_task` is back in `main.py`, running on a
  dedicated writer-clone connection (`SeulgiDB.open_writer_clone`)
  so flush commits don't block the main writer's worker thread.
- `metrics_minutely` accumulates a row per (name, tags, minute) and
  is queryable via `seulgi/scripts/analysis/perf_timeline.py`.

### Phase 5 — diagnostic CLIs

Three host-side read-only tools under
`seulgi/scripts/analysis/`:

- `db_health_audit.py` — per-table COUNT/MAX/gap, age, WAL state,
  PRAGMAs. `--watch` mode for live monitoring during soaks.
- `writer_lock_probe.py` — timed test INSERTs on `metrics_minutely`,
  reports p50/p95/p99 over N samples.
- `wal_checkpoint.py` — standalone WAL checkpoint utility (PASSIVE
  / FULL / RESTART / TRUNCATE).

### Phase 6 — codebase audit reports

Three static / read-only reports under
`seulgi/scripts/analysis/reports/`:

- `silent_rollback_forensic.py` — finds and dates every burst of
  missing row IDs in `trades` / `engine_results` / `signals` /
  `usage_events`; correlates with the `cycles` table.
- `connection_audit.py` — FKs, UNIQUE constraints, indexes,
  triggers, PRAGMAs. Confirms whether the perf indexes from
  2026-05-20 are still in place.
- `code_path_audit.py` — static grep for `except: pass`,
  `return_exceptions=True`, and every `self._conn.execute*` call
  site. Use this when chasing a new silent failure.

## Verify the fix (runbook)

```bash
# 1) Snapshot pre-state
SNAP=seulgi/snapshots/verify_$(date -u +%Y%m%dT%H%M%SZ)
mkdir -p "$SNAP"
cp seulgi/data/dashboard/{dashboard,db_health,scout_funnel,engine_comparison}.txt "$SNAP"/

# 2) Confirm row-ID gaps from earlier are visible
python3 seulgi/scripts/analysis/reports/silent_rollback_forensic.py \
    --table trades --min-burst 20 | head -40

# 3) Live view (one line per 30 s)
python3 seulgi/scripts/analysis/db_health_audit.py --watch &
WATCHER=$!

# 4) Force a cycle reset to trigger the failure mode
docker exec jennie-seulgi python /app/scripts/reset_cycle.py \
    "cycle_verify_$(date -u +%Y%m%dT%H%M%SZ)"

# Expect: chunked-commit log lines in container output, e.g.
#   [reset_cycle] committed chunk 0-50 / 245  (123 ms)

# 5) Watch db_health.txt for 30 minutes
watch -n 5 'head -30 seulgi/data/dashboard/db_health.txt'

# Expect: trades, engine_results, signals, usage_events all show
# age < 60s. Counter columns show err = 0.

# 6) After soak, re-run forensic — gap should not have grown.
python3 seulgi/scripts/analysis/reports/silent_rollback_forensic.py \
    --table trades --min-burst 20

# 7) Writer-lock latency under live load
python3 seulgi/scripts/analysis/writer_lock_probe.py --samples 30

# Expect: p95 < 500ms, no errors.

kill $WATCHER
```

If any of the above fails: check `db_health.txt` for the failing
table + counter; the new logging will name the failing exception.

## How to read the row-ID gaps

`trades.count(*) = 5,387,202` and `trades.max(id) = 5,754,942`.
The arithmetic: 5,754,942 − 5,387,202 = **367,740 IDs missing**.

Those IDs were allocated to INSERT statements that obtained an
autoincrement ID then ROLLED BACK before COMMIT. In aiosqlite's
implicit-transaction mode, an INSERT runs inside a transaction
opened on first modify; the transaction commits when `commit()`
fires. If `commit()` never fires (because the connection's worker
thread is blocked waiting for a lock, then the busy_timeout fires
and aiosqlite gives up), the transaction is implicitly rolled back
when the next BEGIN starts — and the INSERT vanishes.

After Phase 1+R4 lands, the rollback rate should be ~zero. To check:
```bash
python3 seulgi/scripts/analysis/db_health_audit.py | grep gap
# After 30-min soak, "gap" columns for trades/engine_results should
# show the same numbers as before the soak — no NEW rollbacks.
```
