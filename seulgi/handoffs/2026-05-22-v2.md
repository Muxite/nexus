## §1 — root-cause story (the long version)

The handoff at 2026-05-22 07:14 said: "engine fan-out write silence —
TASK-24, instrument and find the broken edge". I did that, then
followed the trace through three layers:

**Layer A: `_engine_should_pause` is the slow read.** Adding the
instrumentation showed `gather START` never firing, then narrowed
to a stall in the `active_engines` filter. Direct DB query
benchmark:

```
balanced/conf40_tp030_sl050: 24 rows in 1387 ms   (← 1.4 s !)
super_scout/all_signals:      0 rows in    0 ms
scout/all_signals:           16 rows in  332 ms
```

The query was using `idx_trades_engine_decided (engine_name=?)`
then `USE TEMP B-TREE FOR ORDER BY closed_at DESC LIMIT 50`. With
~288k rows per engine and no `(engine_name, closed_at)` composite
index, the sort dominated. 20 engines × 1.4 s = 28 s per cache
refresh. The single aiosqlite worker thread queued the reads.

Fix: hot path became O(1) set membership; refresher runs every
TTL=300s as a background task.

**Layer B: `db.batch()` permanently broken once.** After fixing
Layer A, the gather started but then hit
`OperationalError('cannot start a transaction within a transaction')`
at `await self._conn.execute("BEGIN")`. Every subsequent batch
caller hit the same. Diagnosis:

1. A prior batch() got cancelled at an await point (likely the
   wait_for(90s) timing out)
2. The except path runs rollback, but rollback's own await
   re-raised CancelledError
3. The inner try caught Exception not BaseException, so
   CancelledError propagated past the cleanup
4. The connection stayed mid-transaction
5. Next batch's BEGIN failed → permanent break until container
   restart

Fix: batch() now (a) tries a no-op ROLLBACK on entry to clean any
stale state, (b) wraps the cleanup-path rollback in
`asyncio.shield(...)` so a pending cancellation can't unwind it.

**Layer C: Python sqlite3 default isolation_level races BEGIN.**
With Layer B fixed, txn errors STILL happened, traced to Python
sqlite3 module's legacy `isolation_level=DEFERRED`. The module
auto-issues implicit BEGIN before write statements. If one of those
implicit BEGINs interleaves with our explicit BEGIN in batch(), we
get the same nested-transaction error.

Fix: open the connection with `isolation_level=None` — true
autocommit. Explicit `BEGIN` / `COMMIT` in batch() are the only
transaction boundaries; per-row writes outside a batch auto-commit
(cheap on WAL+synchronous=NORMAL).

**Layer D: mega-batch held the global lock too long.** After all
three fixes the gather entered + evaluates ran + writes were
queued, but evaluate END still didn't fire within 90 s. The
mega-batch (20 engines × ~25 markets = ~500 inserts in one
transaction) was holding `_batch_lock` longer than the 90 s
timeout, so every gather then rolled back.

Fix: removed the outer `db.batch()` wrap from `_batched_gather`.
Per-insert autocommit is cheap on WAL; the aiosqlite worker thread
still serialises writes; we no longer block on a giant
transaction.

## §2 — the Stage-2 strip

The relevance LLM (`gemini-2.5-flash-lite`) was making one call per
headline, ~25 markets at a time. The model was returning malformed
JSON ~80% of the time (smart-quote / truncation / schema-drift). The
parse-error branch fell open and kept everything, so the gate was
filtering nothing while costing tokens. Today's burn alone hit $5
on this path.

The replacement is deterministic: `m.similarity >= 0.50`. The 25th
percentile of historically-executed STRONG_YES trades was 0.534, so
this captures most of the profitable bucket. Per-market sim-fail
matches are written to trade rows tagged `not_relevant:SIM_FAIL`
(for funnel attribution); per-headline summary logs as
`sim-gate kept N/M (floor=0.50)`.

`relevance.py` still lives in the repo but is no longer wired into
`engine.process()`. The `RelevanceFilter` class is constructed in
main.py (config still references it) but its `.filter()` method is
never called; only the `_min_top_similarity` attribute is read by
engine.py.

Per-engine `relevance_keep_scores` config keys are ignored. The
`_run_engine` per-engine relevance re-filter was deleted.

## §3 — Phase 5 data foundation

Three new tables capture every input to a future replay harness.
Schema in `db.py`'s `_HIST_SIM_SCHEMA` block, writers in the
"Historical-simulation data foundation" section of `db.py`.

- **`decision_inputs`** — one row per signal: embedding bytes,
  matches JSON (cond_id / question / similarity / mid_yes /
  mid_no / relevance_score), freshness label + dist + age, pre-AI
  universal skips JSON, max similarity, source host. Captured
  fire-and-forget right before `gather START`.

- **`llm_calls`** — schema in place, writer exists, NOT wired into
  ai.py yet. Plan B for when LLM-call replay becomes a priority.

- **`llm_parse_failures`** — Stage-3 parse failures captured with
  raw response (4KB cap) + error message + model. Wired in
  `ai.py:classify_batch` line ~410 via the `db=` constructor
  argument. Drives the Phase 2.2 "categorise failure modes"
  workstream.

The replay harness itself (a `historical_simulate.py` that walks
these tables + `market_price_snaps` and re-runs trader.evaluate
with new configs) is NOT in this cycle. The point of Phase 5 was
to make sure we couldn't paint ourselves into a corner that makes
it impossible later.

## §5 — known limitations the next session should know about

- **Engine-pause refresher is a no-op stub.** Re-enabling it without
  fixing the slow read first will recreate the original hang.

- **The `_write_lock()` shim is intentionally a no-op.** The 8
  callsites still wrap their bodies in `async with _write_lock():`
  for diff-minimality; aiosqlite's worker thread is the real
  serialisation point. Don't add real locking back without
  re-validating against the original Container-6/7 deadlock
  (production-only, not reproduced in replay harness).

- **Lots of `low_similarity` and `not_relevant:SIM_FAIL` skip rows.**
  At sim_floor=0.50 the bot is filtering aggressively. If
  executions stay scarce after the soak, drop the floor to 0.45
  or 0.40 and re-test.

- **OpenRouter cost can still spike.** Budget auto-pause is at $5
  remaining; that's a ~12h buffer at current burn. If you bump the
  cap to $200, the bot will burn through it in ~17 days at
  $11/day (yesterday's number). Move to claude-haiku-4-5 if parse
  failures stay high.

- **The 90s `wait_for(_batched_gather)` is still there as a
  safety belt.** With the batch wrap removed, gather should
  complete in seconds, not 90s. Keep the timeout in place — it's
  cheap and protects against the next unknown hang.
